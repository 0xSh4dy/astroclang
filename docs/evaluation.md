# Evaluation

What the index costs and what it is worth, measured on real C++ rather than
asserted. Every number here comes from a run of `scripts/evaluate.py` or a
script recorded beside it, on the machine described in §1.

---

## 1. Method, and what these numbers are not

**The machine is a laptop, not a benchmark rig.** Intel i5-10210U (4 cores, 8
threads), 15 GB RAM, NVMe, with a desktop session running. It is the machine
the tool was developed on, which makes the numbers representative of using it
and not representative of a quiet server. This matters more than usual here,
and §4 is the reason: on this workload the limiting resource turned out to be
memory, not cores, so runs of the *same configuration* on the same tree vary by
more than 2× depending on what else the machine is doing. Every figure below
says which regime it was measured in.

**Two subjects, chosen to be different from each other.**

| Subject | What it is | Why it is here |
| --- | --- | --- |
| `/usr/src/googletest` | 108 translation units of C++17, templates, multiple inheritance, a large gmock test suite | a real project with a real call graph, where most calls land on code the index holds |
| `cpp/` (this tool's own extractor) | 7 translation units, but each pulls in the entire LLVM 17 and Clang 17 header closure | the stress case: a small project whose analysis is dominated by declarations it deliberately does not index |

Neither subject ships a `compile_commands.json`. The googletest one was
generated with `scripts/make_compdb.py` at `-std=c++17`; the tool's own with
the same script against its CMake configuration. That the standard matters is
not a detail: the first googletest run used `-std=c++14` and lost everything
behind the first `if constexpr`, which appears as a missing symbol rather than
as an error. `cg-index --print-config` prints what a file will be compiled
with, and is the way to check a generated database against the tree.

**What is deliberately not measured:** peak memory of a full parallel run as a
*system* property (see §4 — it is measured, but per worker count), and
correctness against a reference implementation. Correctness is the test
suite's job (`python/tests`), not the evaluation's.

## 2. Indexing

| | googletest |
| --- | --- |
| Translation units | 108 |
| Extractor runs that failed | 0 |
| Translation units with a compiler error | 1 |
| Indexed without a compilation database | 0 |
| Wall time | 124.54 s |
| Seconds per translation unit | 1.15 |
| Peak extractor RSS | 1864.1 MB |

The two failure lines are different things and both are worth having. The first
is the indexer's own report: every one of the 108 extraction processes started
and produced facts. The second is `store.stats()["failed_tus"]`: one translation
unit compiled with an error in it, so anything behind that error is absent from
the index. It is `googletest-death-test_ex_test.cc`, and the error is
`use of undeclared identifier 'GTEST_ENABLE_CATCH_EXCEPTIONS_'` — a macro the
project's real build defines and the compilation database generated by
`scripts/make_compdb.py` does not. That is an artefact of the measurement setup
rather than of the tool, and it is the kind of thing §1 exists to warn about:
`get_index_status` reports the count, `get_diagnostics` returns the message, and
a reader can see that one file's contents are not fully in the index.

The second subject is not given a column here because its indexing cost is not
what it is for: it exists in this document to show what resolution looks like
when a project's analysis is dominated by headers it does not own, which is §6.

`peak extractor RSS` is `getrusage(RUSAGE_CHILDREN).ru_maxrss`, which on Linux
is the **largest single child**, not the sum of concurrent children. It is a
per-translation-unit high-water mark: one unity build (`gmock_all_test.cc`)
needs 1.84 GB on its own. §4 measures the concurrent total separately, and the
difference between those two numbers is the most important thing in this
document.

### Where the 1.8 GB goes

To check whether the extractor is the cost or Clang is, the same file was
compiled with the same arguments and no analysis at all:

```sh
clang++ -std=c++17 -fsyntax-only -I... gmock_all_test.cc
```

| | Peak RSS | Time |
| --- | --- | --- |
| `clang++ -fsyntax-only` | 1840 MB | 35.87 s |
| `cg-index` | 1864 MB | 34.85 s |

The extractor adds about 1.4% over the front end it drives. The memory is the
C++ front end's cost, not this tool's, and no amount of care in the visitor
changes it. What the tool *can* be faulted for is not bounding how many of
those it runs at once — see §4.

those two decisions took the edge count from 656 518 to 910 451, and it is the
reason the numbers here differ from the ones this document first reported.

The share of each kind also moved, which is the more interesting part: type
edges point at declarations, and declarations are exactly what a
per-translation-unit analysis holds as stubs. That is the next section.

## 4. Scaling, and the bottleneck that matters

The number this replaces was wrong, and how it was wrong is worth recording.
A first measurement ran the same tree serially and then in parallel, reported
**3.10×** (369 s then 119 s), and was an artefact: the serial run went first
and read every file from a cold page cache, the parallel run went second and
found them all in memory. Alternating the order and repeating it — the only
way to keep both configurations at the same temperature — gives this instead:

| Round | Serial (`jobs=1`) | Parallel (`jobs=0`) | Speedup |
| --- | ---: | ---: | ---: |
| 1 | 248.22 s | 230.21 s | 1.08× |
| 2 | 240.31 s | 104.86 s | 2.29× |

Same two configurations, same tree, 2.1× apart. Nothing in the program
changed; what changed is what else the machine was doing. That is what a
parallel speedup measured on a laptop actually looks like, and it is why the
figure is not quoted as one number.

Sweeping the worker count steadily, and sampling memory from `/proc` while each
run is in flight, replaces the pair with a curve. `jobs=8` is what `jobs=0`
resolves to on this machine — `min(32, os.cpu_count())`, and `cpu_count()` is 8
— so the last row is what the tool does untouched:

| jobs | seconds | speedup | peak concurrent extractor RSS | swap growth |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 266.19 | 1.00× | 1850.1 MB | +20 MB |
| 2 | 175.53 | 1.52× | 2062.4 MB | +211 MB |
| 4 | 122.97 | 2.16× | 2240.2 MB | +155 MB |
| 8 | 124.54 | 2.14× | 2437.3 MB | 0 MB |

**The speedup saturates at about 2.15×, and the fourth worker is the last one
that buys anything.** Eight workers — the default here — is marginally *slower*
than four and costs 200 MB more. This machine has 4 physical cores, so past
that the extra processes are SMT siblings competing for the same memory
bandwidth: each Clang front end streams a gigabyte and a half of headers
through the same bus, which is not a workload that scales with thread count.

**Peak memory is not the binding constraint, which corrects an earlier claim in
this document.** Peak concurrent extractor RSS rises only from 1.85 GB to
2.44 GB across the whole sweep, because it is dominated by the single unity
build (`gmock_all_test.cc`, 1.84 GB on its own) rather than by the sum of the
workers: the other 107 units are small enough that several can run beside the
big one without moving the peak much. An earlier draft of this section said
eight front ends "drive the machine into swap". They do not. Swap growth during
a run is between 0 and 211 MB, and it is a noisy signal in both directions —
the 0 MB at `jobs=8` follows three runs that had already pushed and pulled the
same pages — so it is reported rather than leaned on.

What the swap figures do show is that this machine was under memory pressure
before the indexer started: the desktop session had roughly 10 GB in swap
before the first run of the sweep. A parallel indexer cannot be measured
cleanly against a box in that state, which is one more reason §1's caveat
applies to every number here.

The number to take away is the ceiling — about **2.15× on four physical
cores** — and the change it argues for: `jobs` should be capped at the physical
core count rather than the logical one, because the default over-provisions on
any SMT machine and the over-provision is not free.

## 5. Query latency

What an agent actually pays. Measured over 200 symbols drawn with a fixed seed
from the project's own functions and methods, and separately against the
single most-called symbol in the index, which is the worst case.

### Ordinary symbols — 200 sampled

| Tool | median | p95 | max | median payload |
| --- | ---: | ---: | ---: | ---: |
| `get_symbol` | 0.34 ms | 1.14 ms | 16.81 ms | 492 B |
| `get_callers` | 0.27 ms | 1.23 ms | 38.68 ms | 539 B |
| `get_callees` | 0.22 ms | 0.65 ms | 2.20 ms | 433 B |
| `get_impact_analysis` | 0.64 ms | 2.88 ms | 28.40 ms | 1204 B |
| `get_source_context` | 0.53 ms | 1.12 ms | 1.31 ms | 2199 B |

The median answer costs half a millisecond and half a kilobyte. The `max`
column is the same code meeting a symbol that is nearly a hub — the sample is
drawn from functions with at least one call edge, and a few of those are
called from everywhere.

### Questions with no subject

| Tool | median | p95 | payload |
| --- | ---: | ---: | ---: |
| `find_symbol` | 0.47 ms | 0.50 ms | 1851 B |
| `search_symbols` | 15.17 ms | 15.68 ms | 2225 B |
| `get_index_status` | 22.21 ms | 22.63 ms | 472 B |

### The worst case

Against `testing::internal::CodeLocation::CodeLocation`, which the index
records as called from 3606 distinct places. Six sweeps of forty repeats each,
reported as the median *of the sweeps* so that one slow sweep cannot be mistaken
for the answer:

| Tool | median | range over sweeps | payload |
| --- | ---: | ---: | ---: |
| `get_callees` | 0.41 ms | 0.38–0.66 | 215 B |
| `get_source_context` | 0.55 ms | 0.52–0.79 | 1982 B |
| `get_symbol` | 25.30 ms | 23.87–29.25 | 546 B |
| `get_impact_analysis` | 35.61 ms | 34.05–44.34 | 11 675 B |
| `get_callers` | 56.20 ms | 55.62–67.50 | 2626 B |

A hub is about 74× slower than a typical symbol on `get_symbol` (25.30 ms
against 0.34 ms), and the cause is one line of SQL rather than the graph design.
`get_symbol` reports the caller and callee *counts*, each an exact
`COUNT(DISTINCT src)`, and a distinct count over N rows is O(N):

```
symbol()              0.03 ms     the row itself
degree in            22.58 ms     COUNT(DISTINCT src) over every edge into it
degree out            0.29 ms     the same query, on a symbol nothing calls
ancestors()           0.05 ms
callers() limit 10   30.52 ms     the list, and the exact count it carries
callees() limit 10    0.31 ms
```

The breakdown accounts for the total: 0.03 + 22.58 + 0.29 + 0.05 ≈ 23 ms of
the 25 ms. `get_callers` on the same symbol costs 56.20 ms because it pays for
the count *and* for picking the caller list (`SELECT DISTINCT ... ORDER BY
s.qualified LIMIT ?`, which must sort every matching row before it can apply
the limit) *and* for the evidence query behind the entries it names.

Counting rows instead of distinct callers would be a different number and a
wrong one — the same function called twice in one file is one caller. It is
left exact, and the cost is confined to the handful of symbols in any project
that are hubs. An agent that asks about `std::string`'s constructor pays 25 ms
once; every other question it asks is sub-millisecond.

**A correction.** An earlier version of this table reported 143.01 ms for
`get_symbol` on this symbol, with 44.73 ms in the distinct count. That figure
does not reproduce. Re-measured three times over, and again in a fresh process
where the first query is 24.9 ms and the fortieth is the same, the answer is
the table above. The old numbers are not revised here, they are withdrawn: the
only thing this document can say about the 143 ms is that something produced
it once, and no measurement since has.

## 6. Semantic resolution

The metric that matters is not "how many edges have a symbol row" — the
extractor mints a stub for every declaration it merely refers to, so that count
is always zero and the ratio always 100%. What says something is *what kind of
thing* each edge lands on.

For googletest, all 910 451 edges:

| Destination | Edges | Share |
| --- | ---: | ---: |
| defined in a project file | 603 359 | 66.3% |
| a stub (declared, body not analyzed) | 246 451 | 27.1% |
| a synthetic identity (anonymous, TU-local) | 60 641 | 6.7% |

That the project share *fell* from the 76.7% an earlier run reported is not a
regression: it is the type edges arriving. A `param_type` or `returns` edge
names a declaration, and a declaration is precisely what a per-translation-unit
analysis holds as a stub when the definition is elsewhere — so restoring a
quarter of a million type edges moves the overall ratio toward the stub column
while leaving the call graph exactly as it was.

And for call edges alone — the ones an agent follows to understand behaviour:

| Destination | Calls | Share |
| --- | ---: | ---: |
| defined in a project file | 87 973 | 45.8% |
| a stub (declared, body not analyzed) | 103 203 | 53.8% |
| a synthetic identity | 774 | 0.4% |

**45.8% of calls resolve to a body the index holds.** That is the honest
headline, and it is lower than the containment and type edges because calls
are what leave the project: googletest calls into libstdc++ constantly, and
system headers are not indexed by default.

The 53.8% is the trade recorded in [`clang-usage.md`](clang-usage.md) §4, made
measurable rather than left to be discovered. Indexing the standard library
would move that number and destroy the graph's usefulness: a question about
`resize` would be answered by libstdc++'s twenty overloads rather than by the
project's own code. The call *sites* are recorded, the identity is exact, and
the body is what is missing — `get_callers("std::vector<int>::resize")` is
answerable and says who calls it; `get_callees` of a stub is empty because
there is nothing to report.

### The second subject, and why it is a worse one

The extractor's own source tree — 6 translation units, 62 739 symbols, 508 348
edges, 356.6 MB of database — reports **0.2% of call edges landing in project
code**: 128 of 73 045. The other 99.8% is 68.8% outside the project and 29.8%
on stubs.

The edge count and the database both grew sharply when the type edges were
fixed, and they grew *here* far more than on googletest — 365 679 to 508 348
edges, 214 MB to 356.6 MB, against a symbol count that barely moved. The reason
is the same one that makes this a bad resolution subject: nearly every
declaration in this tree belongs to LLVM, so the type edges a declaration walk
produces are overwhelmingly edges into somebody else's types. It is a good
demonstration that the type edges were never a rounding error.

That is not a defect in the analysis, and it is worth being precise about why,
because the number looks alarming. Those 6 translation units pull in the whole
LLVM 17 and Clang 17 header closure — 615 files reach the index, of which 12
are this project's own. Almost every declaration in every file's AST belongs to
somebody else, and the tool's own code is a thin layer over it. A `resize` in
this tree is libstdc++'s, and the index says so.

So it is a good stress test — 6 files that produce 365 679 edges is a hard case
for the store — and a useless measure of resolution quality. googletest is the
subject the bold number above comes from, and the reason both are reported is
that a reader should be able to see how much the answer depends on which
project was asked.

## 7. Incremental indexing

One source file touched (a comment appended), then re-indexed:

| | googletest |
| --- | --- |
| Full index | 124.54 s |
| Re-index after one file changed | 6.26 s |
| Translation units re-indexed | 1 |
| Translation units left alone | 107 |
| Speedup | 19.9× |

6.26 s for an 18-line change is the cost of one unity-build translation unit
(`gmock-all.cc` is a file that `#include`s the rest of gmock), and it is the
worst case for this project rather than the typical one: the other 107 units
were not re-analyzed at all. The part that scales with the *project* rather
than with the change is the merge — 2.94 s over 55 725 symbols — and that is
the number to watch as a repository grows.

That both numbers are *lower* than the 9.63 s and 3.28 s reported before the
edge fix is not a speedup anyone implemented. The index holds more now, not
less. It is the spread §1 describes: on this machine, two runs of the same
thing differ by more than the difference being reported, and the honest reading
of a 9.63 s against a 6.26 s is that the incremental path is single-digit
seconds and the merge is a few, not that either improved by a third.

## 8. Bottlenecks found and deliberately not fixed

Each of these was measured, diagnosed, and left alone. None of them is on the
path of a question an agent asks repeatedly.

| Cost | Cause | Fix that was rejected |
| --- | --- | --- |
| `get_index_status` 22 ms | `COUNT(*) FROM raw_edge` scans 910 451 rows | a maintained counter table, or a cheaper approximate count — for a call an agent makes once per session |
| `search_symbols` 15 ms | `LIKE '%text%'` cannot use an index, so it scans every symbol | FTS5 — a second index to keep in sync, for substring search over 55 725 rows that is already fast enough to feel instant |
| `get_symbol` on a hub 24–29 ms | an exact `COUNT(DISTINCT src)` is O(rows) | approximate or cached counts — the exactness is the point |
| `peak extractor RSS` 1.8–2.4 GB | the Clang front end on one unity build | nothing in this tool can fix it; see §4 for what it can fix |

The hub figure carries a range rather than a number because that is the
sweep-to-sweep spread on a laptop with a desktop session on it. The cause is
the same throughout — a distinct count over every edge into a symbol, O(rows)
by construction — and so is the conclusion: it is confined to the handful of
symbols in any project that are hubs, and it is left exact. A single earlier
run recorded 143 ms for the same query against the same index; six sweeps
since put it between 23.9 ms and 29.3 ms, so §5 withdraws that figure rather
than quoting a range with an outlier holding one end of it open.

The last row is the one that is not merely a latency question, and it is the
one an earlier draft of this section got wrong. Worker count is chosen from
`os.cpu_count()` alone, which on an SMT machine over-provisions: this box
reports 8 and has 4 physical cores, and §4 measures that the eighth worker
makes the index marginally *slower*. The remedy is to cap `jobs` at the
physical core count. What the earlier draft claimed — that the parallel indexer
"will swap rather than slow down gracefully" — is not what the measurement
shows, and it has been corrected in §4.

## 9. What these numbers do not say

* **Not a comparison.** Nothing here benchmarks another tool. The claim being
  supported is that the index is affordable and the answers are cheap, not that
  it is faster than something else.
* **Not reproducible to the digit.** §1 and §4 give the reason; the spread on
  the same configuration is larger than most of the differences in this
  document.
* **Not the whole accuracy picture.** §6 measures what edges resolve to. It
  does not measure whether every construct was visited — that is the test
  suite's job, and the corpus is deliberately small and adversarial rather than
  large and representative.
* **Not tuned.** No part of this work was optimized against these numbers
  except where a measurement showed a wrong *answer* — the type edges that were
  silently absent (`architecture.md` §3.4, and §3 above) — or a wrong metric
  (the resolution ratio §6 replaces). Three claims that previously stood in
  these documents as measurements have been removed rather than left standing,
  because re-measuring could not reproduce them: a speedup of 3.10× (§4), a
  query that "went from 53 ms to 0.02 ms" with planner statistics
  (`architecture.md` §3.4), and 143 ms for the worst-case `get_symbol` (§5).
